# スケジューラのバックオフを flowgx で検査した（項目 g の答え）

`flowgx` は状態機械の構造欠陥（終端に到達できない状態、出る辺の無い状態）を検査する。
**「`sched_ready` の安全網は実際に発火しうるか」**を、機械的に答えるために使った。

## 結果：**0 errors**（1 info = 意図した再試行ループ）

```
5 states, 8 transitions
accepting: removed
cycle: queued → visiting → queued
inspect: 1 problem (0 errors)
```

**全状態が `removed` に到達可能** = **バックオフのはしごは必ず期限に到達する**。
つまり **`sched_ready` が「due なのに false」を返す状態は存在しない。**

## なぜ冗長と言えるか（コード側の根拠）

| 事実 | 出典 |
|---|---|
| `sched_ready` は「エントリ無し」または「期限到来」で true | `main.rs:3503` |
| `requeue_fluid` の遅延は**同じバックオフ表**から取る | `main.rs:3511` のコメント |
| `sched_invalidate` はバックオフを**消して**キューの期限を次tickへ**昇格** | `main.rs:3647` |

したがって「キューが due と言う」とき、対応するバックオフは期限到来済みか存在しない →
`!region.is_warm(x, z) || !sched_ready(x, y, z)` の**後半は発火しない**。

**流体 tick の `sched_ready` は、外れない安全網である。**

## 削除しない理由（今は）

**削除は独立した1コミットにする。** 根拠は揃ったが、
- 3ループ（lava / water / hopper）で同じ変更をする
- `verify.sh` が緑のままであることを確認する
- **変異チェックに登録して、削除しても挙動が変わらないことを示す**

**「証明できたから消す」ではなく「消しても変わらないことをテストで示す」**のが、この枝で
5つの手書き表を消してきたときと同じ手順である。

## 副産物：状態機械が文書になった

`machine.py` は**スケジューラの仕様**である。`sched_ready` の意味を変える変更は、
**このファイルを赤くする**（あるいは更新を強制する）。コメントではなく**検査可能な成果物**として残す。
