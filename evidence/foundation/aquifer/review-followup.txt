- Exhaustive grep for `±8` in the path regions (`:1930-2010`, `:3180-3300`, plus `prelim_est|prelim_min|est_min|min_est` call sites) finds **no remaining plain `+8`/`-8`**; the only other `8` literals are the cache size, the `(y-…)` scan offsets, and comment text. No build-mode difference from a bare `+8/-8`.
- The wrapped sentinel stays benign: with `run_depth` from `minecraft:surface` (`:1871-1877`, `n*2.75 + 3.0 + r*0.25`, `n` ≈ [-1,1] → 0…≈6), `MAX.wrapping_add(r).wrapping_sub(8)` lands at `MAX-8+r` for `0<r<8`, so `scan_top < est_min` at `:2342` takes the `continue` before the plain `scan_top - est_min + 1` (`:2345`) and `vals[(y - est_min)]` (`:2391`).

**Residual (latent, not currently reachable):** those two plain expressions are unguarded arithmetic on the sentinel. If `run_depth` ever exceeded 8 (i.e. surface noise `n > ~1.8`), the double wrap would land `est_min` *negative*, the `scan_top < est_min` guard would no longer fire, and `:2345` would overflow (debug panic, release garbage/giant `Vec`). Java has the same wrap in the `+8` step but no equivalent downstream subtraction, so this would be a divergence by build mode if it ever occurred. With the current noise range it does not occur.

- `tools/aquifer_oracle.py:78-84` (state loop): `assert len(got) == 5 and got[:3] == want[:3]` then `assert type(want[3]) is float and type(got[3]) is float` before `assert got[3] == want[3]`.

- A `bool` is rejected: `True == 1.0` is true, so the equality alone would pass; the `type(...) is float` conjunct is the rejector (`type(True) is bool`, and `bool` is not exactly `float`). `rejected()` catches `AssertionError`, so the case fails closed. An `int` `1` would be rejected too.
- The `0.0`-row case at test line 40 and the 1.0-row case differ only in the request value, so both exercise the same assertion.

**Adjacent residual gap (not the asked case):** `validate()` never type-checks integer positions (`got[:3] == want` and `got[:3] == want[:3]` accept `True` for `1`), and result `prelim` rows are only length-checked and de-duplicated (`:73-77`) — they are not cross-checked against `request["prelim"]` columns, unlike density rows. A fixture with substituted but unique prelim coordinates would pass `validate()`/`validate_fixture()`; only the whole-fixture equality in `main()` and the Rust replay would catch it. No current test claims otherwise, so this is a coverage gap, not a false assertion.
