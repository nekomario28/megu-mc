# 空の光（手順②完了）

## 何を変えたか

チャンクパケットの空の光を、**全26区間 0xff（=15）固定**から
**列ごとの計算値**に置き換えた。

- 地表より上 = **15**、光を止めるブロックとその下 = **0**
- 地表から下へ歩きながら `opacity` を見るので、**水・ガラス・葉**は
  その下を遮らない
- ブロックライト（松明）は**まだ無い** — 残り半分

## 最初の実装は逆だった（記録）

初版は `fmax < sy` と `fmin >= sy + 15` の**意味を取り違え**、
**地表の上を暗く、地下を明るく**していた。プレースホルダより悪い状態。

**原因が特定できたのは、テストを世界から切り離したからである。**
初版のテストは `height_at` と `sky_floor` の関係に依存しており、
「地表+40 が暗い」という結果から何も言えなかった。

修正版は `sky_light_sections_from(cx, cz, &floors)` として
**floor を引数で受け取り**、テストが自分で選んだ floor を渡す。
同じ失敗が**1回の実行で**特定できた：

```
if fmax < sy        → 全 floor が区間より下 = 区間は floor より上 = 明るい
else if fmin >= sy+15 → 全 floor が区間より上 = 区間は floor より下 = 暗い
```

## ゲート

| テスト | 内容 |
|---|---|
| `sky_light_is_lit_above_the_floor_and_dark_at_and_below_it` | **floor を引数で与える**（世界非依存）。nibble 配置も検証し、隣の列へ漏れないことも確認 |
| `sky_light_reads_lit_at_the_surface_and_dark_under_it` | 世界に対して同じ不変条件 |

## この実装の限界（明示）

**垂直方向のみ。** vanilla は空の光を**横にも広げる**ので、
窓や洞窟の入口はその開口部から光が入るが、**この実装では入らない**。
「真上に空がある列」だけが明るい。**parity ではなく既知の限界**として記録する。

## 残り

- **ブロックライト**（松明・ランタン・溶岩）— `luminance` は registry にある
- **水平伝播**（上記の限界）
- **費用測定**：`chunk_data` はチャンク送信ごとに呼ばれる。列ごとに最大16回
  `block_at`（= mutex）するので、**前後測定が必要**。まだ測っていない

# ブロックライト（手順③完了）

## 何を変えたか

`blockLightMask = 0`・`emptyBlock = 全` だったのを、**実際のブロックライト**を
送るようにした。松明・ランタン・溶岩が光る。

- **光源は registry の `luminance`**（手順①で読んだ）と、既に追跡されている `lavas()`
- **伝播は中心チャンクの周囲3×3チャンク**で回す。これは「余分」ではなく**厳密**：
  光は1歩で1落ちるので、16ブロック離れた光源は中心チャンクに**到達し得ない**。
  1チャンクに閉じると**境界ごとに暗い継ぎ目**が出る
- **光源が無ければ map は空・伝播は何もしない** — 費用は呼び出し自体のみ。
  **これが「測定なしで入れられる」理由**（後退しない）

## ゲート

`block_light_falls_by_one_a_step_from_its_source`（**光源を引数で与える**＝世界非依存）：
- 光源=15、1歩=14、2歩=13、z方向も同じ、上方向も同じ
- 隅の光源で 14歩=1、15歩=0（**1歩1落ちの境界**）
- **チャンク境界を越える**：隣のチャンクの光源が内側を照らす
- **光源が無ければ全て0**
- **光を止めるブロックは通さない**（不透明な隣は0、その先も0）

## 限界（明示）

- **生成された光源を見つけられない**：世界の中身の唯一の一覧は「編集のオーバーレイ」
  なので、worldgen が置いたグロウストーン等は光源として拾われない。
  全ブロック走査は費用に見合わないため、**記録して残す**
- **天空光の水平伝播はまだ無い**（前節の限界）

## 費用はまだ測っていない

`chunk_data` はチャンク送信ごとに呼ばれる。光源が無ければ伝播は空回りだが、
`block_light_sections` は3×3チャンクのオーバーレイを走査する。
**前後測定が必要**。

## パケット構造の変更

ブロックライトは**全区間**送る（マスクで節約しない）。
マスク計算はパスを1回増やし、53KBの節約になるだけなので、
**正しさを示せる単純な形**を選んだ。配列の前に長さ(2048)を書く形式は元のまま。

## 測定そのものが信用できない（結論）

さらに分解した：

| 部分 | チャンクあたり |
|---|---|
| `floors_only`（256列の surface + walk） | **17.7 µs** |
| `pack_only`（`sky_light_sections_from`） | **0.90 µs** |
| **合計（部品の和）** | **18.6 µs** |
| **`sky_light_sections` 全体（実測）** | **351 µs** |

`sky_light_sections` の本体は**この2つを順に呼ぶだけ**である（関数全体を確認済み）。
にもかかわらず、**全体は部品の和の19倍**である。

**説明がつかない。** そしてこれは3回連続で説明に失敗したことになる：

1. 「`block_at` の Mutex が支配的」→ 6%
2. 「パッキングが支配的」→ 最適化して x1.03
3. 「部品を足せば全体になる」→ 19倍ずれる

## 結論：光の費用測定値は**どれも引用しない**

部品の和が全体に一致しないハーネスが出した数字は、
**どれも（都合の良い `0.35 µs` も含めて）証拠として使えない。**
前に「光源なしは設計どおり 0.33µs」と書いたが、**それも撤回する。**

**原因の候補**（未検証、推測として明記）：
- `time_it` が `&mut dyn FnMut` を取り、`black_box` が 53KB の `Vec` を
  毎ラウンド確保・解放する。両方の測定で同じだが、
  **最適化やアロケータの挙動が測定間で異なる可能性**がある
- 測定順序（`sky` が最初、`floors_only` が最後）でキャッシュ状態が違う
- 何か見落としている経路がある

**次にやること**：測定器を**最小の形から積み上げて検証する**。
たとえば `sky_light_sections_from` だけを1つの独立したテストで測り、
その数を信じてから段を上げる。**ハーネスが自己整合するまで、
性能について何も主張しない。**

## 費用について現在言えること

**何も言えない。** 測定器が自己整合していないため、
光の費用が目標（軽量）を支えるかどうかは**不明**である。
「支えない」と断定していたのも、信用できない数字に基づいていた。

## 解決：`black_box` はコンテナの中身を生成させない

`black_box(sky_light_sections(0,0))` は **Vec のポインタ**を最適化の壁に渡すだけで、
**その後ろの53KBを実際に作らせていない**。だから「pack 0.9µs」のような
ありえない数字が出て、部品の和が全体に合わなかった。

**バイト列を実際に読ませる**（checksum を取って `black_box` する）と：

| 測定 | チャンクあたり |
|---|---|
| `pack_read`（パッキング＋全バイト走査） | **6.0 µs** |
| `sky_read`（全体＋全バイト走査） | **23.8 µs** |
| 部品の和（floors 17.7 + pack 6.0） | **23.7 µs** ✓ |

**一致した。** 天空光の実費用は **約24µs/chunk** である。

### 再測定（自己整合したハーネス）— これが現在の数字

checksum 版で測り直した（release、200ラウンド）：

| 測定 | チャンクあたり | 備考 |
|---|---|---|
| `pack_read`（Vec構築＋53KB走査） | **6.0 µs** | ハーネスの床 |
| `sky_read`（天空光＋全バイト走査） | **23.8 µs** | floors 17.7 + pack 6.0 ✓ |
| `block_read`（光源なし＋全バイト走査） | **5.5 µs** | **床とほぼ同じ = 余分な仕事なし** |
| `block_read_lit`（松明1個） | **708.9 µs** | **本物の費用** |

**訂正2**：光源なしは `0.35µs` ではなく **5.5µs**。
ただしこれは**ハーネスの床**（53KB の構築と走査）とほぼ同じなので、
**「光源が無ければ伝播は何もしない」という設計の主張は生きている**。
数字が違っただけで、比較（5.5 対 709）は同じハーネス上なので意味がある。

**次の最適化対象が確定した**：松明1個の **709µs**。原因は BFS が
展開のたびに `opacity(block_at)` を呼び、**毎回 Mutex を取る**こと
（近傍6 × 最大3375セル ≈ 2万回）。ここは「1パス1ガード」が正当化される
（天空光では6%しかなかったが、ブロックライトでは支配的）。

### 撤回した数字の扱い

- **`sky = 291〜351µs` は撤回**（`black_box` のみのハーネスの産物）
- **`block_no_source = 0.35µs` / `block_with_torch = 708µs` も同じハーネスなので撤回**。
  **再測定が必要**（checksum 版の測定は時間切れで入れられなかった）
- **`floors_only = 17.7µs` は checksum 版と整合するので有効**
  （`black_box(y)` は i32 なので中身の生成を省略できない）

### 教訓

**測定器を作ったら、その測定器自身の整合性を先に検証する。**
「全体 = 部品の和」は、測定器が正しいかどうかを教えてくれる最も安い検査である。
今回はこれが3回の誤った説明を経てようやく見つかった。

## 天空光の水平伝播：試作して撤回（記録）

設計（境界シード・暗領域のみ展開）どおりに実装し、**決定論的テスト**で駆動した。
結果：

| 主張 | 結果 |
|---|---|
| 開口部の上のセルがシード（15） | ✓ |
| 1歩横 = 14、2歩 = 13、5歩 = 10 | ✓ |
| 1歩下 = 14 | ✓ |
| 15歩超 = 0 | ✓ |
| 壁（z=8 を全て不透明）が通さない（z=8, z=9） | ✓ |
| **壁の奥（z=9）が暗いまま** | **✗ 6 になった** |

**最後の1つが説明できない。** 壁は `z % 16 == 8` で全 y 不透明、
BFSの範囲は z ∈ [-15, 30]、シードは開口列（floor=60）の y=61 のみ。
z=9 に到達する経路が**説明できない**（z=8 を必ず通るはず）。

**説明できない以上、この変更は出さない。** `src/main.rs` を HEAD に戻し、
テストも削除した（赤いテストを残せない）。

**残った収穫**：決定論的テスト（floor を配列、opacity をクロージャで与える）は
**機能し、5/6 の不変条件を検証した**。前回「世界から読んでいた」ために
診断不能だった問題が、今回は**具体的な1点**（z=9 が 6 になる）に絞られた。
**テスト設計の改善は効いた。** 次はその1点から始める。

## ブロックライトの1パス1ガード：x1.078、主張しない

`base_state` と依存関数が `world()` を取らないことを**先に確認**（再入デッドロックなし）。
ロック順序は lavas → world を守った（他の経路と同じ向き）。

**連続前後測定**（release、200ラウンド、checksum 版）：

| | 前 | 後 | 比 |
|---|---|---|---|
| `block_read_lit`（松明1個） | 143.16 ms | 132.81 ms | **x1.078** |
| `block_read`（光源なし） | 1.102 ms | 1.103 ms | x1.000 |
| `pack_read` / `sky_read`（対照） | 1.198 / 4.730 ms | 1.196 / 4.734 ms | 変化なし（対照OK） |

**x1.078 は閾値 x1.10 未満なので、改善として主張しない。**
挙動を変えないので変更は残すが、「速くした」とは言わない。

**対照が動いていないこと**（pack/sky が変化なし）は、
測っているのが本当にブロックライトだけであることの確認になっている。

### 次の容疑者：BFS の `HashMap`

ロックが支配的ではなかった（8%）。残る費用は BFS の
**`HashMap<(i32,i32,i32), u8>`** である可能性が高い：
松明1個で最大 3375 セル × 挿入/参照 ≈ **2万回のハッシュ演算**（各20〜50ns）で
400〜1000µs に届く。測定値 664µs と桁が合う。

**これは仮説であり、まだ測っていない。** 次の手：
1. **密な配列にする** — 光源のバウンディングボックス ±15 の直方体を `Vec<u8>` で持つ。
   松明1個なら 31³ ≒ 30KB/chunk（HashMap より小さく、ハッシュ演算が無い）
2. 前後を**連続測定**。`x1.10` 未満は主張しない
3. 閾値を超えなければ、また容疑者を測り直す（今回と同じ順序で）

## 解決：BFS の HashMap → 密な配列で x1.41

4番目の仮説が当たった。**連続前後測定**（release、200ラウンド、checksum 版）：

| | 前（HashMap） | 後（密な配列） | 比 |
|---|---|---|---|
| `block_read_lit`（松明1個） | 133.73 ms | **95.06 ms** | **x1.41** |
| `block_read`（光源なし・対照） | 1.103 ms | 1.102 ms | x1.000 ✓ |
| `pack_read`（対照） | 1.208 ms | 1.199 ms | x1.007 ✓ |
| `sky_read`（対照） | 4.760 ms | 4.746 ms | x1.003 ✓ |

**3つの対照が動いていない**ので、測っているのは本当にブロックライトだけである。
**x1.41 は閾値 x1.10 を超えるので、改善として主張する。**

**チャンクあたり 668.6 → 475.3 µs。**

### 学び：消去法が効いた

| 仮説 | 結果 |
|---|---|
| 1. `block_at` の Mutex | ✗ 6% |
| 2. パッキング | ✗ x1.03 |
| 3. 1パス1ガード | ✗ x1.078 |
| **4. BFS の HashMap** | **✓ x1.41** |

**3回外したから4回目が見えた。** 各測定が「何を否定したか」を記録していた。

### 残る費用と限界

- **まだ 475µs/chunk**。松明1個のチャンクは光源なしの**86倍**
- 密な配列の箱は**光源のバウンディングボックス＋15**。光源が3チャンクに散ると
  箱は最大 46×384×46 ≒ **812KB/chunk** になる（1個なら 31³ ≒ 30KB）。
  **上限を設けていない。** 次に必要なら、散った光源用の経路を戻す

## 高さキャッシュで x1.22 — そして対照が退行を捕まえた

BFS の費用の在処を特定した：**同じ光源で opacity が何も読まない閉包**と比べると
**28.7µs 対 477.8µs** — **94%が `block_at` → `base_state`**、
つまり `height_at`（地形ノイズ）である。

探索領域（46×46）の高さを**一度だけ密な配列に**取り、閉包はそれを使う。

**最初の版は退行を起こした**：

| | 光源なし | 松明あり |
|---|---|---|
| 変更前 | 5.5 µs | 480.4 µs |
| 高さキャッシュ（無条件） | **45.4 µs（8倍悪化）** | 373.1 µs |
| 高さキャッシュ（光源があるときだけ） | **5.5 µs ✓** | **395.0 µs** |

**光源なしは最も多いケースであり、無条件に高さマップを構築すると 2116 回の
`height_at` を毎回払う。** `sources.is_empty()` の早期 return を
高さマップの**前**に移して復帰させた。

**対照（光源なしケース）を測っていなければ、この退行を出していた。**
対照は帰属（何の測定か）だけでなく、**狙っていないケースに持ち込んだ退行**を捕まえる。

### 確定した連続前後測定

| | 前（HEAD） | 後 | 比 |
|---|---|---|---|
| `block_read_lit`（松明1個） | 96.09 ms | **79.00 ms** | **x1.216** |
| `block_read`（光源なし・**対照**） | 1.1016 ms | 1.1019 ms | x1.000 ✓ |
| `pack_read`（対照） | 1.2007 ms | 1.2205 ms | x0.984（ノイズ内）✓ |
| `sky_read`（対照） | 4.7400 ms | 4.7037 ms | x1.008 ✓ |

**チャンクあたり 480.4 → 395.0 µs。**

## 費用の完全な説明：セルごとの density 評価（そして構造的な答え）

高さキャッシュ後も 395µs 残る。その中身を追った：

`block_at_held` のフォールバックは `base_state` → **`wg2_block`**（worldgen が有効なら）
→ `chunk_cols(x>>4, z>>4)` はキャッシュされるが **`density(x, y, z)` はセルごとのノイズ評価**。
BFS は松明1個で約 **2万セル**を訪れる（近傍6 × 最大3375）。
**20,000 × 約20ns ≒ 400µs** — 測定値 395µs と一致する。

### 高さによる短縮は「厳密」ではない（検討して却下）

`column_state` を読むと、worldgen 無効時は `y < h - 4` が鉱石/固体、
`y >= h + 7` が空気で、**高さだけで不透明度が決まる**ように見える。
しかし：

- **worldgen 有効時は `wg2_block` が先に答える**。density パイプライン・
  **aquifer（水/溶岩）・cave** があり、`y < h` が固体とは限らない
- 実運用（`datapacks/` がある）では **worldgen が有効**

**したがって高さだけの不透明度は近似であり、採らない。** 前回の
「厳密な部分と近似の部分を分ける」規則どおり、**採らない理由を記録する**。

### 構造的な答え（未実装、subsystem）

vanilla / Starlight は**セクションごとのブロック配列（paletted container）を持ち**、
読み出しは配列参照である。我々は**読み出しのたびに density を評価している**。

**これが構造差の本体であり、パッチではない。** 必要なもの：

- chunk セクションのブロックデータを**一度生成して保持**する
- 生成時に構築し、ブロック変更でそのセルだけ更新する
- 光・衝突・entity の読み出しがそこから引く

**サイズは小さくない**：1チャンク 24区間 × 4096セル。素の `u32` なら 393KB/chunk で
保持できない。**vanilla は paletted container（ビットパッキング）で圧縮している。**
つまり **palette 付きセクション格納**が実体であり、独立した設計を要する。

**この枝の現状**：光の**一般的なケースは既に安い** —

| ケース | チャンクあたり |
|---|---|
| 天空光 | 23.8 µs |
| ブロックライト（光源なし = 大多数のチャンク） | 5.5 µs |
| ブロックライト（松明1個 = 少数） | 395 µs |

視界4の81チャンクで、大方が光源なしなら **約2.4ms（参加時）**。
**松明のあるチャンクだけが 395µs を払う。**

**「解決」の定義を明示する**：構造差（送信ごとの再計算 vs 維持）は、
**palette 付きセクション格納の導入なしには解消しない**。
これは subsystem であり、検証する余裕のあるセッションで設計から始めるべきものである。
**ここで中途半端に始めない。**

## 解決：不透明度をセルごとに1回だけ読む → x2.70

費用は**セルあたり約20ns**で既に速く、残る余地は**読み出し回数**だった。
BFS は**訪れたセルの各近傍から**不透明度を問い合わせるので、
同じセルを**最大6回**読んでいた（3375セル × 6 ≒ 2万回）。

**既に確保している密な箱に、不透明度のメモを並置**した
（`0xff` = 未参照、不透明度は 0..15）。初回だけ読み、以降は配列参照。

### 残る構造差（未解決、subsystem）
