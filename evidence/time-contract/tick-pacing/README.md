# tick のdrift補正pacing

## なぜ

`sleep(TICK_MS)` は「寝た時間」で次のtickを待つ。
tick処理が5ms超過すると、次も5ms超過して積み上がる。
20TPSを標榜するなら時刻ドリフトは看過できない。

## 変更

次の締切を**前回の締切 + 1インタバル**で導出する。
超過していても締切は据え置きなので、ドリフトが累積しない。

さらに「1インタバル以上超過したら締切を now に張り直す」。
catch-upしようとspinすると、過負荷のサーバーに仕事を足すだけになる。

## 出どころ

PR #2（`fix/audit-1-security-runtime`）の `56a6e79` にあったpacing。
ただしあちらの20TPSは素朴で、効果持続・炉・空気・TTL・移動係数を
変換しておらず取り込めない。**pacing部分だけを移植した。**

## ゲート

`next_deadline` を本番から抽出して検証する。

- 100tickで締切が正確に 100 インタバル進む（ドリフトなし）
- 超過が無ければ締切を据え置く（cadenceが滑らない）
- 超過があれば now に張り直す（catch-up spin をしない）

負の対照：再アンカーをやめると `reanchored < deadline` で失敗。
spinし続ける実装はテストで検出できる。

## 境界

実サーバーでのtick遅延・超過頻度は未測定。
ドリフト補正の**効果量**ではなく**規則**を検証している。
