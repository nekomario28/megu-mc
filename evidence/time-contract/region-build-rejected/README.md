# region構築のVec+sort+dedup — 測定して不採用

## 候補

`refresh_hot` が20TPS同一条件で支配的（Actor 88–97%、炉 44–47%）。
 HashSetへの重複insertを、Vecへpush→sort→dedupへ置き換える候補を作った。
 中心が重なるほど同じchunkを何度もhash probeするのがコストなので、
 重複は比較で済む方が有利という見込み。

## 測定（同一fixture・同一runner・release・各3プロセス）

| fixture | 変更前 tick | 変更後 tick | 比 | hot_regions 比 |
|---|---:|---:|---:|---:|
| 空 | 1170.91µs | 1193.06µs | x0.98 | x0.92 |
| idle Actor 1 | 10044.34µs | 8184.32µs | **x1.23** | x1.27 |
| 休止炉400 | 19039.56µs | 17214.06µs | **x1.11** | x1.26 |

プロセスCPU合計 0.2766s → 0.3469s。

## 不採用の理由

まばらな中心では10–29%速いが、**密集した中心では40%遅い**。
プレイヤーは基地やスポーンに集まるので、密集側は現実的な負荷形状。
全体として良くないのでrevertした。

sortのコストは候補数（中心数×面積）に比例し、hashの重複skipは
実際の集合サイズに比例する。密集すると候補数が集合サイズを大きく超えるため
sortが不利になる。`direct_cost` の分岐と同じ構造の問題。

`(200,-200)` の欠落として検出した。独立oracleがあるおかげで即座に特定できた。
