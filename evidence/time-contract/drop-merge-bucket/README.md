# dropマージのO(n²)をセルバケットで解消

## 計測（同一fixture・各3プロセス・HEAD基準）

| fixture | tick | drops stage |
|---|---:|---:|
| entity_heavy | 666,976µs -> 339,037µs (**x1.97**) | 478,372µs -> 149,337µs (**x3.20**) |
| entity_heavy_furnaces | 674,305µs -> 347,242µs (**x1.94**) | 478,266µs -> 149,892µs (**x3.19**) |
| 他の6fixture | x0.99–1.00 | x0.96–1.00 |

プロセスCPU 1.7401–1.7457s -> 1.0227–1.0241s。

## 何をしたか

`drop_tick` のマージは全ペア比較の O(n²) だった。
600ドロップで約18万ペア/tick。

セルバケットに変えた。`|ax-bx| < 0.5` なら `floor(ax)` と `floor(bx)` は
高々1違いなので、**同じセルと隣接26セル**に入るものだけが候補。

## 等価性の担保

- `i` は元の順序で回す
- 候補は近傍27セルから集め、`j > i` でフィルタし、**元index昇順**で試す
- 最初の一致でmergeしてbreak

近傍外の `j` は距離判定で必ず失敗するので、除いても最初の一致は変わらない。
**sortしてから比較する案は等価ではない**（吸収されるドロップが変わる）。

条件の順序も替えた。安いitem一致と距離判定を先にし、
`comps` のVec比較は実際の候補にだけ回す。意味は変わらない。

## 見つけた実バグ: 座標極端時のオーバーフロー

`cx + dx` が i32 上限でオーバーフローしてpanicした（`attempt to add with overflow`）。
`d.x.floor() as i32` は範囲外を飽和させるので、世界の端のドロップで
本番でも同じことが起きうる。

`checked_add` に直した。wrappingではセルキーがエイリアスして
別のドロップと誤ってマージする可能性があるので使わない。

## 残る

`entity_heavy` は依然 339ms/tick。drops stage はまだ149msで支配的。
バケット化で劇的に減ったが、まだ O(n×近傍数) で、
600ドロップが狭い範囲に集中すると近傍も600になる。
**空間的に分散した負荷が対象**。密集は別途必要。

`environment` が27%あるのも未調査。
