# 1.21.1 Rustサーバー全体を完成へ収束させる計画

Status: **実行方針A〜E・worldgenの受け入れ方針・資源上限はユーザー承認済み。**
計画・原因特定・設計判断はmain agentが担当し、実装担当へ具体的な境界を渡す。
承認済みの方針と、各候補の実行済み検証・統合完了は区別する。

対象は個別のテスト修理ではなく、mc-spine 全体。目標・完成の契約は
[PLAN](../PLAN.md) の M2（同じ入力で遊べる範囲のvanilla一致）、M3（同じ仕事での軽量性）、
M4（要求範囲の準拠）を維持する。範囲を黙って縮めて「完成」と呼ばない。
この文書は進め方と優先順位の見直しを持ち、現在の実装状況や測定値の別台帳にはしない。

## なぜ収束していなかったか

- 個別featureの差分・対応数・テスト数を追い、接続から保存再開まで動く製品の出口への
  寄与をタスク選択の基準にできていなかった。
- chunkの値・生成済み状態・破棄の責任が分離する共通問題を残し、個々の植生や構造物の
  症状を先に修正していた。根本改革の調査はあるが実装へ進められていなかった。
- parser、配置、後処理、tick、保存、通信の部品別完了が、機能全体の完了に接続していなかった。
- 統合前の候補・レビュー・報告を増やし、次の作業が依存できる正本を更新できていなかった。
- 変更されていない範囲まで検証を繰り返し、実行費用の見積りと得られる判断材料の釣り合いを
  確認していなかった。検証基盤の修理が、プロジェクト本体の主線を占めていた。

既存の[共通実行基盤の計画](../kernel-convergence-plan.md)や
[Horizon再利用判断](../../evidence/foundation/horizon-reuse/README.md)は活用する。
ただし、過去の対応数・完成率・「数個の共通基盤で全仕様を扱える」という見通しを、
現在の実装や残工数の証明として使わない。1.21.1の固定vanillaが挙動の基準であり、
他プロジェクトの設計参照はコードの直接コピーやライセンス変更の承認ではない。

## 主線と実行順

| 段階 | 行うこと | 出口 |
|---|---|---|
| 0. 現在の作業を収束 | 完成候補、未完作業、検証未実行を区別し、今回のテスト基盤修理・既存候補を所定の条件で統合する。新しい周辺整備を増やさない | 次の実装が依存する正本と、残る保留理由が一意に分かる |
| 1. chunk状態の整合性 | 値・生成段階の完了状態・依存する出力の破棄を一貫した責任で管理する | 実際の容量境界・破棄・再生成を通して、同じ入力と順序で状態が壊れない。旧所有者・旧経路を残さない |
| 2. 生成からruntimeへの接続 | 段階ごとの近傍参照、block変更の副作用、tick予約、生成結果の受け渡しを既存所有者へ接続する | 本番経路で生成→更新→保存→再読込を通し、同じstage・入力の参照と比較できる |
| 3. M2を操作単位で閉じる | 接続・移動、破壊設置、所持品・収納、クラフト・精錬、明暗・時間・天候、戦闘・死亡/リスポーン、基本mobを、既存実装から最後までつなぐ | PLANの各操作が実通信、別接続からの再取得、保存再開を含めて受け入れ条件を満たす |
| 4. M3を同じ仕事で測る | M2で受け入れた機能・負荷を固定し、CPU時間・RSS・tick遅延をvanillaと比較する | 機能を省略せず20TPSと軽量性の条件を満たす |
| 5. 要求範囲と配布を閉じる | M4の残件、対象Modの実経路、データ来歴・配布条件を確認する | 要求した範囲と検証済み範囲が一致し、公開判断の未決事項が解消される |

これは必要な依存順であり、独立したM2機能や来歴確認まで完全直列にする指示ではない。
worldgenの全残差解消を、無関係なゲーム操作の実装開始条件にしない。
性能上の明らかな異常は早期に計測できるが、M3達成の主張には同じ仕事の比較を必要とする。

## 根本改革を巨大な書き換えにしない

最初の実装単位は、既に問題が測定されたcarve stageの所有権と破棄の整合性とする。
関連する候補は `t3/chunk-state-reform` の `5caca0b`（調査・仕様であって製品実装ではない）。
その仕様と使い捨てパッチを無検討で取り込まず、次を先に確定する。

- **ユーザー承認済み：初回修正ではWG高さ情報の保持上限4096を維持する。**
  feature側の384も容量変更の対象にせず、値・生成済み状態・依存出力の整合性を直す。
  WG側を実質384へ縮小する実装も、この承認には含まれない。
- 値の挿入、生成開始の記録、破棄、再挿入、順序キューの整合性を、全呼び出し経路で定義する。
- 「破棄しなければ通る」テストではなく、本当に容量境界を超える検証を置く。
- テスト経路の挿入と提案された `debug_assert!` の不整合を解消してから実装する。

一つの責任を移したら旧経路を削除する。並列の世界状態、第二のtick処理、単に既存状態を
包むだけの所有者は増やさない。キャッシュ容量変更、並列化、native意味論変更を同じ修正に混ぜない。
ファイルを短くすること自体を目的にせず、観測済みの故障を閉じる境界で変更する。

## 機能を最後まで完成させる単位

各機能は「実装済み」「本番経路に接続済み」「vanilla対照済み」を分けて扱う。
既存の[実行台帳](../implementation-checklist.md)を使い、同じ内容のチェックリストを増やさない。

- 例：構造物は配置セルだけでなく、必要なblock entity・loot・spawner・近傍更新・保存再読込まで
  つながって初めて、その要求範囲を閉じる。
- 同じ基盤が原因の不具合はまとめて直す。代表例で故障の原因と修正を確認し、同じ経路を使う
  機能群へ広げる。「似ている」「同名の関数がある」だけでは同じ原因としない。
- 入力順・RNG・stage・writerを固定して比較する。生成時とtick後の差を混ぜない。
- 既存の部品・参照データ・通常経路を再利用する。新たな道具は、具体的に足りない確認だけを担う。

## 承認された実行方針（A〜E）

### A — 統合を一つの経路へ収束させる

統合担当をmain agentに固定し、作業単位が受け入れ条件を満たしたところでまとめて正本へ入れる。
報告書だけを追加して判断を先送りしたり、同じ候補に独立レビューを際限なく重ねたりしない。
最初の対象は既存のworldgen・テスト基盤修理候補 `82799b4`。その次に独立した貢献者向け整備候補を扱う。
候補の検証結果は、source・入力・実行artifact・終了値に結び付ける。

候補側の `tools/evidence_receipt.py` はRust testのsource/artifact/filterを結ぶ既存の道具として再利用する。
それ単独では全wire・mutation・native比較を証明しない。主担当が各検証の元ログとscopeを結び付け、
未実行や失敗を含めた統合判定をする。短報の数値やreceiptのPASS一つだけで全体を合格にしない。
この計画の承認はローカル統合の方針であり、push・PR・公開の承認ではない。

### B — 比較の入口と結果の集計を共通化する

既存のfixture比較とsculkの検証を呼ぶ薄い実行入口を整備し、各実行の入力、stage、writer、
差分、skip、終了値を元のartifactから集計する。比較器や参照実行器を作り直さない。
実行していないfixture、欠落した入力、古い結果を成功にしない。手書きの集計値を正本にしない。
これは今後の実装事項であり、単一コマンドが既に存在する・全fixtureが再実行可能という主張ではない。

### C — worldgenは共通原因から閉じる

順序はchunk-state整合性 → 生成stageとruntimeへの受け渡し → structure start選択 → 残るfeature差分。
複数seed・biome・dimensionの参照は保存して再利用し、必要な不足分だけ採取する。
jar・EULA・来歴・共有ホストの制約は引き続き守る。

**原因未確定の区別:** キノコの書込みが保存結果に残らない観測はあるが、LIGHT/postProcessが
削除したとは証明されていない。`ChunkStatus`や後処理は調べる境界であって、確定した原因ではない。
`nether_fossil`のstart選択も、既存の説明で閉じた観測と未解決の不具合を分け、同じ調査を繰り返さない。

worldgenの受け入れは、事前に固定したN個のseedの集合について、全構造物定義と全dimensionを
適用対象に応じて網羅する有限の行列とし、同じ入力・順序・生成stageの比較で差分0を要求する。
biome境界も行列で扱う。Nの値・seed・座標・各機能の正の実行例は、既存captureの棚卸し後、
比較開始前にmain agentが固定する。結果を見て対象を入れ替えたり、未対応をskipして合格にしない。
セルだけでなく、対象構造物のpayloadや保存結果など既存の受け入れ契約も維持する。
これは有限の受け入れ集合であり、全seedに対する数学的な同値証明ではない。

### D — M2の独立機能はworldgenと並行して閉じる

共有chunk状態に触れないゲーム操作は、worldgenの全残差を待たずに進める。
既存のJava oracleとRust probeを使い、実通信・状態更新・保存再読込までつなぐ。
同じ状態所有者を複数担当が同時に変更しない。M3達成の判定と`GEN`ロックの分割は、
状態の整合性と比較負荷が定まってから行う。

### E — 判断と実装を分ける

計画・原因特定・設計・統合判定はmain agentが担う。実装担当へ未決の設計を丸投げしない。
DeepSeek flashには境界と期待する検証を決めた実装・機械的移植・計測を渡す。
新しい担当を増やす前に、既存担当の仕事を収束できるかを確認する。

## 進行と検証の運用

- 共有状態を扱う主線の実装所有者は一人。並列担当は、境界が決まった独立機能や参照データに限定する。
- 担当の成果物は、原則として「報告だけ」ではなく、正本へ統合可能な動作確認済みの一単位にする。
  未解決の設計判断は先に明示し、任意の既定値を実装してから承認を求めない。
- 同じソース・入力・実行環境・検証目的に対する証拠は再利用する。変更に直接関係する確認を先に行い、
  統合候補が固まってから必要な広域検証を行う。
- **承認された変更:** 通常のローカル統合は、変更経路と依存先に対応するmutationを明示的に選び、
  baseline成功 → 変異のassertion失敗を2回確認 → 復元後成功を要求する。範囲と選定根拠を記録し、
  選択0件・compile error・crashを検出成功にしない。検証基盤そのものを変えた場合は、その基盤の否定対照も行う。
- 全mutationは定期的な包括監査へ分離する。承認時の候補は424件であり、414件という先の説明は誤り。
  全件未実行を成功にせず、選択実行の合格と全campaignの完了を別表示する。
  代償は、統合時点で非選択経路の検出力低下を直ちには発見できないこと。定期監査で赤になれば一次原因を追う。
  定期実行の自動スケジュールはまだ設定しておらず、設定済みとは報告しない。
- Rustの通常・並列回帰、wire、adapter、層、debtなど、既存の非mutation統合ゲートは維持する。
  ソース・入力・環境が同一と確認できる既存結果を再利用できるが、変更後へ無条件には引き継がない。
  `tests/verify.sh` は現時点では全mutationを呼ぶ従来の入口であり、選択統合用の入口整備は別の実装事項。
  選択実行だけで同スクリプトの全体PASSを主張しない。
- 実行予算は実際に変更された経路から見積もる。バイト不変の `touch` 再ビルドをmutation費用としない。
  時間・メモリ・ディスクの見通しを立ててから重い検証を開始する。
- 報告は「今回閉じた製品上の境界」「次の一つの阻害要因」「未実行」を中心にする。
  コミット数・テスト数・資料数だけを進捗としない。

## 承認された資源予算

CPUはホストの論理CPU総数の**合計60%まで**、メモリは**最大12GB程度**をプロジェクトの実行上限とする。
各担当にこの上限を重複して与えるのではなく、同時実行の合計で守る。必要量が小さければ小さい予算を使う。

- 16論理CPUのホストならsystemdの`CPUQuota=960%`が9.6 CPU相当。`60%`は0.6 CPUであり意味が異なる。
  Cargoのjobsはまず9までを目安にし、freshなCPU可用性・実測メモリ・同居ジョブに合わせる。
  Cargo jobsを増やしても単一crateの再コンパイルが比例して速くなるとは仮定しない。
- メモリ上限の指定例は`MemoryMax=12G`。これは利用可能な上限であって、常に12Gを確保・使用する指示ではない。
  実行前のresource gate、heavy leaseの取得→起動→bind→解放、named unitと明示的な時間上限を維持する。
- ホストの空きメモリ・ディスク・同時使用量を確認する。上限内でもheadroom不足なら、仕事を直列化・縮小する。
  OOM後に同じ形で再実行しない。既に進んでいる有効なジョブを、上限緩和だけのために再起動しない。
- 生成順の意味を検査する直列テストと、並列回帰のスレッド数はCPU上限とは別の検証条件である。
  CPUを使えるようにするために、その検証条件を無条件で変えない。

## 今は行わないこと

- 全面リライト、別エンジンへの乗り換え、一般化だけを目的とする新しい抽象層。
- 状態の整合性を確認する前のsnapshot/merge方式のworldgen並列化。
- 完成済み候補を統合せず、新しい独立候補・重複調査・レビューを増やすこと。
- 正本と無関係な文書美化、名前変更、大規模な機械的ファイル分割。
- 根拠のない完成率・納期・全seed一致・軽量性の主張。
- 自動的な公開、PR操作、ブランチ削除、他者の未コミット作業の整理。

## 次の判断

1. 承認された選択mutation方針で既存候補と検証状態を収束させる。未実行を明示し、他の必須ゲートは維持する。
2. 承認されたWG上限4096の維持を前提に、最初のchunk-state修正の仕様の矛盾を解消する。
3. その修正を実装・通常経路で検証・統合してから、次の共有責任へ進む。

本計画は「短期間で全Minecraft互換が完成する」という見積りではない。
共通原因を先に直し、既存実装をつなぎ、完了した変更を正本へ収束させるための作業方針である。
