# 最終目標への計画

Status: 実装中。欠陥の残件と完了判定の正本は [close-defects](close-defects/README.md)。
この文書は目標・検証契約・作業順を持ち、過去のチェックポイントやソースの行数を複製しない。
**ユーザー指示により実画面・KDE経由の試験は不要。接続と操作はCLI経由で検証する。**

## 目標とチェックポイント

Minecraft Java 1.21.1（protocol 767）の超軽量サーバーを作り、観測可能なvanilla挙動を維持する。
必要なModとの互換も、コンパイルだけでなく実際の経路で確認する。
以下は中間到達点であり、未修正項目がある状態を「すべて完了」とは呼ばない。

| 段階 | 完了の契約 |
|---|---|
| M1 測定可能 | CLIクライアントが接続・操作でき、代表負荷を固定し、vanillaと同じ仕事で比較できる |
| M2 遊べる | 移動・破壊設置・所持品・クラフト・精錬・収納・明暗・昼夜・天候・戦闘・死亡/リスポーン・基本mobを含むセッションが完走し、同じ入力でvanillaと結果が一致する |
| M3 軽量の証明 | M2の同一負荷・同一設定・20TPSで、vanillaよりCPU時間やメモリが小さい |
| M4 準拠 | エンティティ・レッドストーン・ディメンション・コマンドを含む要求範囲が埋まり、要素ごとの一致を確認する |

相違を列挙することは調査には必要だが、近似を文書化するだけではvanilla維持の要求を閉じない。
現状をM1達成や全機能準拠とは扱わない。

代表負荷の初回測定（`tools/load_compare.sh`、20秒窓×3、同一ホスト・同一移動列・圧縮なし）は
**CPUが mc-spine 21.47s 対 vanilla 16.18s（約x1.33）**、RSSは mc-spine 122 MiB 対 vanilla 1168 MiB だった。
**M3の「CPUも小さい」は未達**であり、idle の小さいCPU値を軽量の一般則に使わない。
追試で `MC_SPINE_WG=old`（フラット）は **0.34s** だった。データパック地形生成が mc-spine の CPU の
ほぼ全てで、tick・チャンク配信・I/O のコアは vanilla より遥かに軽い。**M3 の律速は地形生成器**である。
証拠と限界は [代表負荷比較](../evidence/gameplay/load-compare/README.md) にある。

## 合格条件

| 条件 | 必要な証拠 |
|---|---|
| G1 同じ仕事で軽量 | 同一seed・機能・view/simulation distance・代表負荷のback-to-back比較。CPU時間とメモリを測る |
| G2 同じ結果 | 同一入力列で、ブロック・衝突・ダメージ・ドロップ/個数・釣り・RNG消費・イベント時刻・保存/再読込の結果を照合する |
| G3 20TPS | 固定した代表負荷でtickの50ms予算を検査する。基準周期への切替と、負荷時に予算内であることは別の証明 |
| G4 CLIで操作可能 | 実通信の接続・チャンク復号・移動・操作をassertで検査する。送信側の更新だけでなく、新しい接続で状態を再取得する |

CLIで既に検査した範囲と限界は [CLIクライアントの証拠](../evidence/gameplay/cli-client/README.md) にある。
この範囲を戦闘などを含むM2全体の一致へ広げない。
アイドル比較やdebug CIの受信時間は診断用であり、G1/G3の代表負荷の証明ではない。
ノイズ床は4%。x1.10未満の改善は主張せず、入力や計測器が不適切なら旧測定を撤回する。

代表負荷はプレイヤー、チャンク、エンティティ、配線、炉/ホッパーなどの仕事量を数値で固定する。
fixtureを変えたら、旧測定との比較可能性を再判定する。片側に存在しない機能を黙って省略しない。

## 作業順と所有者

直近の実装順は [close-defectsの作業順](close-defects/README.md#作業順と所有) に集約する。
検証済みコミットはチェックポイントであり、残件があれば次のパスへ進む。

長期の設計は次の文書が所有する。

- [foundation](foundation/README.md): 共有registry、キュー、Entity framework、永続化、チャンクパイプライン。
- [gameplay](gameplay/README.md): データ駆動の挙動、衝突形状、光、植生など。
- [time-contract](time-contract/README.md): tickと保存期間の単位、20TPSへの切替。
- [mod-compatibility](mod-compatibility/README.md): Java backendとModの実経路。

層の抽出はファイルを短くする競争ではない。共有値を下位に置き、状態と呼び出しの所有者を分ける。
ファイル長だけからCPUの支配箇所を推定しない。
生成系の実ソースのゲートと、その射影の限界は [module-layers](../evidence/foundation/module-layers/README.md) にある。
設計図が無循環でも実装の無循環や挙動不変を証明したことにはならない。

基盤後の機能拡張は、既存の素子を使うレッドストーン伝播、Entity frameworkを使う型追加、
Nether/End、プレイヤー/世界機構・コマンドへ進む。どれも同一入力のvanilla対照を要求する。
座標換算や時間に触る変更では、その契約のゲートを再実行する。

## 横断的な規律

- 資産がregistry。新しい手書き表の前に `tools/asset_coverage.py` で中身を調べる。
  衝突形状を`block/empty`のラベルで代用しない。
- 1つの振る舞い・状態の所有者は1つ。並行した世界/効果の状態や不要な設定モードを作らない。
  名前の付いた消費者が現れる前に一般化したスケジューラを作らない。
- 必須ゲートの未実行は成功ではない。通常の入口は `tests/verify.sh`。
  意図した失敗と前後の正常系、復元後に本当に再ビルドされた出自まで確認する。
- Cargoが出したartifactを検査する。推測した`target/debug`の古い実行ファイルを使わない。
  検証の終了値をログ整形や外側のパイプで消さない。
- 独立レビューは実質的な変更ごとに範囲を固定する。静的推論と実行した結果を分ける。
  `main`へこの統合ブランチをそのままマージしない。
- Pumpkin/Starlight/Lithium/FerriteCoreは設計・挙動の参照であり、コードや文面を写さない。
  静的`javap`、手書きモデル、コンテナへの`black_box`を実行時の証明へ読み替えない。

判断の理由は [choices](close-defects/choices.md) が持つ。
gxkitは検査対象に合う道具を使い、モデルの健全性を実装の効果と混同しない。
`chartgx`による測定図と`docgx`による文書検査はまだ未実施。利用していない道具を実績へ数えない。
