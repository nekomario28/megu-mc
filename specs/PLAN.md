## 1. 最終目標と、段階的な「完了」

**最終目標**：Minecraft Java 1.21.1（protocol 767）の**超軽量**サーバで、
**観測可能な挙動は vanilla のまま**、必要な Mod も使える。

この目標は**機能面では無限**である（エンティティ130種、レッドストーン全域、3ディメンション、
約60コマンド）。だから「完了」を段階に分け、**各段で証明できることを決める**。

| 段 | 名前 | 完了の契約 | 証拠 |
|---|---|---|---|
| **M1** | **測定可能** | 実クライアントが接続でき、「代表負荷」が数値で固定され、vanilla と**同じ仕事**で比較できる | 比較レポート（下記 G1〜G4 を全て埋める） |
| **M2** | **遊べる** | 実クライアントで「最初の1時間」が遊べる：接続・地形・移動・破壊設置・インベントリ・クラフト・精錬・チェスト・明暗・昼夜・天候・戦闘・死亡/リスポーン・基本mob | スクリプト化した実クライアントのセッションが protocol error 無しで完走し、**同じセッションを vanilla で走らせた結果と一致する** |
| **M3** | **軽量の証明** | M2 の同一負荷で vanilla より軽い | 同一 seed・view/simulation distance・負荷の back-to-back 比較。**ノイズ床 4%、x1.10 未満は主張しない** |
| **M4** | **準拠** | エンティティ型・レッドストーン・ディメンション・コマンドが埋まる | 要素ごとの一致。**許容する差分は列挙して理由を書く** |

**現在は M1 の手前である。** M1 が無いまま機能を足すと、「軽量」も「vanilla 準拠」も
**反証不能な主張**になる。**機能追加より M1 を先にやる。**

## 6. 横断的な規律

1. **資産が registry**。手書き表を書く前に `tools/asset_coverage.py` を走らせる。
2. **ガードは落ちられることを証明する**。`tools/mutation_check.sh` にエントリを足す。
   **落ちられないテストはテストが無いより悪い。**
3. **測ってから変える**。back-to-back、ノイズ床 4%、**x1.10 未満は主張しない**。
   **測定を無効化されたら取り下げを書く。**
4. **計測器が自己矛盾したら計測器を疑う**（このセッションで2回、正解だった）。
5. **1つの振る舞いの所有者は1つ**。2つ目を書く前に既存を探す。**名前は一致しない**
   （`settle_gravity` と `falling_tick`）。
6. **レビューは実質的な変更につき1回**、範囲を固定した問いで。effort を選び既定で最大を費やさない。
   **pi 経由**：`pi --print --model 'openai/gpt-6.1-sol:high' "$(cat 問い)" < diff`。
7. **1コミットずつ、各段で検証**。`verify.sh` は `&&` で連結。
8. **`main` へそのままマージしない**（issue #7 REQUEST CHANGES が未解決）。

## 7. 未解明の欠陥（S1 と並行して返す）

### 7.1 落下テストが並列実行で落ちる — **解決（原因は変異の測定）**

**失敗の署名が変異と一致していた。** 失敗は `air` があるべき位置にある、という形だった：

| 変異 | 期待される結果 |
|---|---|
| `if false`（支持除去の分岐を殺す） | 何もスケジュールされない → 砂は動かない → `base+2` は **air** ✓ |
| 手書きリスト（`st` 判定を3状態に） | コンクリートパウダーが落ちない → **air** ✓ |

**つまり測っていたのは変異そのものだった。** 変異チェックの直後に同じシェルで
`cargo test` を走らせており、**復元が効いていない経路があった**。

**現在の状態**：park を解除し、`--test-threads=8` を**5回連続**で
**103 passed / 0 failed**、変異チェックは **5 proved / 0 parked**。
変異スクリプトは起動時に残骸を検出したら拒否し、全ての制御可能な終了経路で復元する。

**この欠陥について3度主張を変えた**（決定論的 → 撤回 → 撤回の根拠が誤り → 署名一致で解決）。
**教訓**：**失敗の署名が原因候補の効果と一致するかを確認する。** 一致していれば、
その候補を外す前に「なぜ一致するのか」を説明せよ。

落下を使う3テストが `--test-threads=8` で**4回連続失敗**。`air` があるべき位置に砂が無い。

| 実行 | 結果 |
|---|---|
| 全スイート `--test-threads=1` | 緑（失敗時あり） |
| 全スイート `--test-threads=8` | **4/4 失敗** |
| フィルタ `fall`（1thread） | **3 passed / 3 failed** |
| `sand_falls` 単独 + `--nocapture` | 列もキューも**正しく見える** |

世界を書き換えてロックを取らないテストは**機械的走査では見つからなかった**。
**この欠陥について2度主張を反転させた**（1度目は古いバイナリを測った撤回で、それが誤りだった）。

**現在は名前を付けて park している**（`#[ignore = "...PLAN.md section 7..."]`）。
変異ジョブは park 数を表示するので、**park で緑にすることはできない**：
```
mutation check: 0 proved, 0 not a gate, 5 parked, 0 skipped
```

## 9. やらないと決めたこと

- **一般化したスケジューラ**を、名前の付いた消費者が現れる前に作らない。
- **並行した世界/効果の状態**を作らない。
- **設定モードを増やさない**。
- **Pumpkin / Starlight / Lithium / FerriteCore のコードと文面を写さない**（設計と挙動は参照する）。
- **`black_box` をコンテナに当てて中身を読ませようとしない**。
- **静的 `javap` を実行時測定の代わりにしない**。
