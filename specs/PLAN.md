## 1. 最終目標と、段階的な「完了」

**最終目標**：Minecraft Java 1.21.1（protocol 767）の**超軽量**サーバで、
**観測可能な挙動は vanilla のまま**、必要な Mod も使える。

この目標は**機能面では無限**である（エンティティ130種、レッドストーン全域、3ディメンション、
約60コマンド）。だから「完了」を段階に分け、**各段で証明できることを決める**。

| 段 | 名前 | 完了の契約 | 証拠 |
|---|---|---|---|
| **M1** | **測定可能** | 実クライアントが接続でき、「代表負荷」が数値で固定され、vanilla と**同じ仕事**で比較できる | 比較レポート（下記 G1〜G4 を全て埋める） |
| **M2** | **遊べる** | 実クライアントで「最初の1時間」が遊べる：接続・地形・移動・破壊設置・インベントリ・クラフト・精錬・チェスト・明暗・昼夜・天候・戦闘・死亡/リスポーン・基本mob | スクリプト化した実クライアントのセッションが protocol error 無しで完走し、**同じセッションを vanilla で走らせた結果と一致する** |
| **M3** | **軽量の証明** | M2 の同一負荷で vanilla より軽い | 同一 seed・view/simulation distance・負荷の back-to-back 比較。**ノイズ床 4%、x1.10 未満は主張しない** |
| **M4** | **準拠** | エンティティ型・レッドストーン・ディメンション・コマンドが埋まる | 要素ごとの一致。**許容する差分は列挙して理由を書く** |

**現在は M1 の手前である。** M1 が無いまま機能を足すと、「軽量」も「vanilla 準拠」も
**反証不能な主張**になる。**機能追加より M1 を先にやる。**

## 6. 横断的な規律

1. **資産が registry**。手書き表を書く前に `tools/asset_coverage.py` を走らせる。
2. **ガードは落ちられることを証明する**。`tools/mutation_check.sh` にエントリを足す。
   **落ちられないテストはテストが無いより悪い。**
3. **測ってから変える**。back-to-back、ノイズ床 4%、**x1.10 未満は主張しない**。
   **測定を無効化されたら取り下げを書く。**
4. **計測器が自己矛盾したら計測器を疑う**（このセッションで2回、正解だった）。
5. **1つの振る舞いの所有者は1つ**。2つ目を書く前に既存を探す。**名前は一致しない**
   （`settle_gravity` と `falling_tick`）。
6. **レビューは実質的な変更につき1回**、範囲を固定した問いで。effort を選び既定で最大を費やさない。
   **pi 経由**：`pi --print --model 'openai/gpt-6.1-sol:high' "$(cat 問い)" < diff`。
7. **1コミットずつ、各段で検証**。`verify.sh` は `&&` で連結。
8. **`main` へそのままマージしない**（issue #7 REQUEST CHANGES が未解決）。

## 7. 未解明の欠陥（S1 と並行して返す）

### 7.1 落下テストが並列実行で落ちる — **解決：変異チェックがビルドキャッシュを汚していた**

**原因**：`tools/mutation_check.sh` の復元が `mv` だった。`mv` は元ファイルに**バックアップの mtime**
（= `cp` した時刻 = **変異版バイナリをビルドした時刻より古い**）を与える。すると cargo は
**「最新」と判断して変異版のテストバイナリを再利用する**。ソースはディスク上で正しいのに、
**バイナリがそこからビルドされていなかった**。

**これが全ての観測を説明する**：
- 変異チェックの**直後**に走らせると決定的に失敗する（4/4、5回連続）
- 直接走らせると時々通る（**再ビルドが起きた時だけ**）
- 失敗の署名が変異の効果と一致する（`if false` は支持除去の分岐を殺す → 砂が動かない → **air** ✓）
- 「古いバイナリ」という私の初期の直感は**正しかった**（その後の撤回が誤りだった）

**修正**：`mv` をやめ `cp` + `touch` にする（`touch` がソースの mtime を今にし、
cargo に再ビルドさせる）。

**検証**：変異チェック（5 proved）の**直後**の直列スイートが **103 passed / 0 failed**。
修正前は同じ順序で 3 failed だった。

**この欠陥について4度主張を変えた**（決定論的 → 撤回 → 撤回の根拠が誤り → 署名一致 →
**真因はビルドキャッシュ**）。5回連続で通った実行に基づいて「解決」と書いたのも**誤りで**、
その5回は再ビルドが起きた回だった。

**教訓**：**ソースを編集する道具は、ビルドキャッシュを無効化しなければならない。**
ファイルを正しく戻すことと、**その内容がビルドに使われること**は別である。

## 13. depsgx による S2.2 の前提検査 → **循環が見つかった**

`depsgx` で既存モジュールの層を検査 → **3 errors**：

```
error feature   cycle: feature → tree → feature
error tree      layer-violation: tree (layer 4) depends on feature (layer 3)
error worldgen  layer-violation: worldgen (layer 4) depends on feature (layer 3)
```

証拠：[evidence/foundation/module-layers](../../evidence/foundation/module-layers/README.md)

**S2.2 の第一の仕事は「抽出」ではなく「循環を壊すこと」である。**
光エンジンを新モジュールへ出しても、**そのモジュールは循環に加わるだけ**で層は良くならない。

**順序（改訂）**：
1. `feature.rs` が `tree::` / `worldgen::` を参照している箇所を列挙し、
   **registry の責務か**を1つずつ判定する（そうなら呼び出し側へ押し出せる）
2. 押し出せないものだけを下位層へ移す → **`depsgx` が 0 errors になるまで**
3. **その後で**光エンジンの抽出（1抽出=1コミット、テストが緑のまま）

**盲点**：`cached_lookup` / `effects` / `java_compat` / `landing` / `world_rng` が
「到達不能」と出るのは、`main.rs` が裸の `landing::` で呼ぶため私の辺の抽出が拾えていないから。
**dead code ではない。**
