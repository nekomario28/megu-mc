# 03 — 光エンジン（luminance + opacity）

Status: 設計。**消費者は既に存在し、その消費者は今「嘘をついている」**。

## 現状（実測）

`chunk_data` を送るパケットは光の枠を**既に持っている**が、中身が固定：

```rust
write_varint(&mut p, 1); p.extend_from_slice(&0x3ffffffi64.to_be_bytes()); // skyLightMask  = 全26区間
write_varint(&mut p, 0);                                                  // blockLightMask = 0
write_varint(&mut p, 0);                                                  // emptySky
write_varint(&mut p, 1); p.extend_from_slice(&0x3ffffffi64.to_be_bytes()); // emptyBlock = 全
write_varint(&mut p, 26);
for _ in 0..26 { write_varint(&mut p, 2048); p.extend_from_slice(&[0xffu8; 2048]); }
```

- **空の光を全て 0xff（=15）で送っている** → 世界はどこでも「真昼」
- **ブロックライトは空（0）** → **松明・ランタン・溶岩が光らない**
- `opacity` は一切使われていない（`state_flags` 経由の遮蔽判定とは別）

**つまり光エンジンの消費者は存在する。** 今日の値は**プレースホルダであり、
実装は「新しい消費者を作る」ではなく「既存の消費者に本当の値を渡す」。**
`DESIGN.md` の「消費者が居てから部品を作る」を満たす。

## データ（既にある）

`assets/pblocks.json`(現在は `assets/block_states_1211.json` に移行済み。`luminance` / `light_block`)の**状態ごと**のフィールド：

| フィールド | 意味 | 分布（実測） |
|---|---|---|
| `luminance` | その状態が放つ光 0..15 | 35,723状態、16種。34,097 が 0 |
| `opacity` | その状態が光を通すか（減衰） | 35,723状態、3種 |

`tools/asset_coverage.py --field luminance` が両方を出す。

## 契約

1. **空の光**：地表より上は 15。`opacity` に応じて下へ減衰し、
   完全な遮蔽で 0 まで。既存の `height_at`（地表の高さ）が出発点になる
2. **ブロックの光**：`luminance > 0` の状態から BFS で 15 から減衰して広がる。
   光源が無ければ**全て 0**（現状と同じ＝後退しない）
3. `0xff` の固定値を**実際の値に置き換える**。枠（マスク・長さ）は変わらない

**これは近似ではない。** 現状の「常に15」のほうが近似であり、
実装は**近似をやめる**方向。したがって
「vanilla との一致」を主張できる最初の光の状態になる。

## 費用

**これが最大の懸念。** 光は**チャンク送信時に計算**するなら
（`chunk_data` は既に O(区間×4096) の走査をしている）、追加は
**BFS 1回/チャンク + 空の減衰**。既存の走査に相乗りできる可能性が高い。

- **測ってから決める**：`chunk_data` の現在の費用を測る（送信はtick外なので
  `profile_tick` の stage には出ない。`CHUNK` 用の測定が必要）
- 光の再計算が要るのは**状態が変わったとき**だけ。今は送信ごとに計算しているので、
  **変化時に計算して保持する**ほうが安い可能性がある（`saved_state` の扱いも要検討）

## 検証

1. **症状そのもの**：松明を置いた位置のブロックライトが 15、隣が 14、2つ隣が 13。
   松明が無ければ 0
2. **空の光**：地表より上は 15、`opacity` の高いブロックの下は減衰
3. **資産を独立に読む**：`luminance`/`opacity` を `block_states_1211.json` から読み、
   全状態で registry の値と一致
4. **負の対照**：`luminance` を無視すると症状テストが落ちる
5. **費用**：`chunk_data` の前後を**連続測定**。`x1.10` 未満は主張しない

## 順序

1. `BReg` に `luminance` / `opacity` を状態ごとに読む（**消費者はパケット**）
2. **空の光**を `height_at` + `opacity` から計算し、`0xff` 固定をやめる
   （光源が無くても正しくなる＝この時点で世界の見た目が変わる）
3. **ブロックの光**の BFS（光源が無ければ 0 なので後退しない）
4. `chunk_data` の費用を前後測定

**2 と 3 を分けて入れる**のは、2 だけで正しくなり、
3 は光源が置かれたときだけ効くため。**各段階で前後を測る。**

## 軽量化mod の設計解析（[別紙](../light-mod-analysis.md)）

**vanilla 1.20+ は Starlight の方式を取り込んでいる**（Starlight の文書自身が
obsoletion notice でそう述べている）。したがって参照すべきは
**vanilla 1.21.1 自身の光エンジン**であり、Starlight の文書はその原則の説明である。
ライセンスが許容的でないため**設計のみ参照、コードは写さない**。

**この枝に直接効く3原則**：

1. **光データは「非空セクションの1半径」にしか存在しない** —
   我々は常に26区間を計算・送信している（地形は数区間にしか無いのに）
2. **既に15の隣接を高さマップで除外する** — Starlight はこれで
   キューを 2000 → 300 に減らした。我々の天空光の水平伝播の設計にそのまま効く。
   **z=9 が 6 になる件もこの領域（種の選び方と除外）**
3. **光は変化時に維持する**（送信ごとに計算しない） —
   我々はチャンク送信ごとに 475µs で計算し直している。
   **測定値の根本原因はここにある可能性が高い**

## 残り：天空光の水平伝播（設計）

現状は**垂直のみ**。窓や洞窟の入口から光が入らない。

### 素朴な実装が高くつく理由

天空光の種は「空が見える全てのブロック」＝**空気の領域全体**である。
そこから BFS すると、**地表より上の巨大な領域を全部走査**することになる。

### 安くする鍵：種は「暗い領域に接する殻」だけでよい

明るい領域は既に列計算で 15 と分かっている。BFS が新しく塗れるのは
**暗い領域（`y <= floor[列]`）だけ**なので、

1. 種 = **`floor+1`（明るい）のセルで、隣が暗いもの**。チャンクあたり 256 個
2. BFS の展開先を **`y <= floor[隣接列]` のセルに限定**する
   → 明るい領域を再導出しない

これで費用は**境界に接する空洞の体積**に比例し、空全体に比例しない。

**これは近似ではない**（光は1歩で1落ちるので、届く範囲は 15 歩に限られる）。
ただし `floor` の定義は列ごとに独立なので、**水平に伝播した光が別の列の
`floor` を下げる**ことはない — つまり「洞窟の奥が 0 のまま」になる可能性がある。
**これは近似であり、明示する。**

### 実装前に確かめること（解析の候補）

vanilla の `LightEngine` が
1. `opacity` をどう減衰に使うか（`max(1, opacity)` か、`opacity` そのものか）
2. 空の光の初期値をどこから置くか（chunk の上端から下向きか、列ごとか）
3. 再計算の単位（ブロック変更ごとか、チャンクごとか）

**私の実装は 1 を `max(1, opacity)` と仮定しており、これは推測である。**
`javap` か vanilla を走らせた採取で確認する価値がある。
**推測のまま parity を主張しないために、ここを解析の第一候補にする。**

### 共通部品の候補

ブロックライトの BFS（`block_light_sections_from`）と天空光の水平伝播は
**同じ形**（種＋減衰＋最大値のBFS）である。2つ目の消費者が現れるので、
**伝播エンジンを1つにして、種と減衰関数を渡す**形にできる。
今は消費者が1つなので作らない（規則どおり）。
